# 개인 포트폴리오 웹사이트 (dwoobae.com) 설계

- 작성일: 2026-07-27
- 상태: 사용자 승인 대기
- 관련 자료: [제로베이스 포트폴리오 아티클](https://zero-base.co.kr/event/media_insight_contents_FE_frontend_portfolio_web), [GitHub 프로필](https://github.com/dongwoobae)

## 1. 목적과 포지셔닝

취업/이직 지원용 개인 포트폴리오 웹사이트.

핵심 메시지:

> **"실사용자가 있는 서비스를 수주부터 설계·개발·운영까지 — 프론트엔드까지 직접 구현하며 — 혼자 책임지는 백엔드 중심 풀스택 개발자"**

- 모든 페이지는 이 문장을 증명하는 방향으로 작성한다. "무엇을 만들 줄 안다"가 아니라 "만든 것이 지금 돌아가고 있다"를 보여준다.
- 회사 네임밸류 대신 **의뢰 → 운영 → 소개로 후속 수주** 서사를 전면에 둔다.
- 백엔드·DevOps 관점(파이프라인 설계, 동시성 제어, 보안 경계, 인프라 운영)을 강조한다.
- 프론트엔드 역량은 별도 섹션으로 주장하지 않고 **증거로 스며들게** 한다: 케이스 스터디의 "프론트 구현 하이라이트" 항목 + 포트폴리오 사이트 자체의 완성도(반응형·접근성·디테일)로 증명한다. 근거는 운영 서비스 4개의 UI를 전부 직접 구현했다는 사실이다.
- **AI 시대의 개발 방식을 첫 화면에서 정면으로 내세운다**: Claude Code 등 AI 도구를 적극 활용해 개발 속도를 내되, **원하는 동작을 테스트·E2E로 고정(Vitest·PGlite 통합 테스트·Playwright)하고 CI 게이트로 지키는 방식**으로 품질을 책임진다는 메시지. AI 사용을 숨기지 않고 "AI를 잘 쓰는 개발자 = 검증 체계를 갖춘 개발자"라는 프레임으로 제시한다. GitHub 프로필의 개발 철학("AI가 코드를 빠르게 생성할 수 있는 시대일수록 중요한 것은 무엇을 왜 만들어야 하는가")과 일관되게 연결한다.
- 언어: 한국어 기본. 영어 버전은 범위 외(추후 필요 시 별도 설계).

- 인증·세션 없음. 전 페이지 공개.

### 도메인 이전 계획 (2027-07)

`dongwoobae.com`을 사려다 `dwoobae.com`을 등록했고 Cloudflare Registrar는 환불을 하지 않는다. 1년간 `dwoobae.com`으로 운영하고 2027-07 갱신 시점에 `dongwoobae.com`으로 옮긴다.

이전 시 URL이 바뀌므로 설계에 다음을 반영한다.

- **사이트 URL을 코드에 하드코딩하지 않는다.** `NEXT_PUBLIC_SITE_URL` 환경변수를 단일 출처로 삼고, sitemap·JSON-LD·OG·canonical이 모두 이 값을 참조한다. 도메인 이전은 환경변수와 `wrangler.jsonc`의 routes만 바꾸면 되도록 한다.
- **끊어진 링크 위험:** 지원서·이력서에 적어 배포한 `dwoobae.com` 링크는 도메인을 놓는 순간 죽는다. 이전 시점에 **두 도메인을 1년 겹쳐 보유하고 `dwoobae.com` → `dongwoobae.com` 301 리다이렉트**를 걸어두는 것을 권한다(연 1~2만 원 수준). Cloudflare Redirect Rule로 처리하면 Worker 코드 변경이 필요 없다.
- 이전 전까지는 `dwoobae.com`으로 외부 백링크를 적극적으로 쌓지 않는다. 검색 유입보다 지원서에 직접 링크를 넣는 용도가 주력이므로 실익이 크지 않다.

```

/projects            프로젝트 목록 — 착수 순 정렬, 기간·상태 표기 (운영 중 / 진행 중 / 완료)
/projects/[slug]     케이스 스터디 상세
/notes               딥다이브 노트 목록 — 날짜순 피드가 아니라 "프로젝트별 그룹" 뷰가 기본
/notes/[slug]        노트 상세
/about               타임라인(지구환경과학 → 네이버클라우드 데브옵스 과정 → 실무 + 수주 이력) + 개발 철학
```

- SEO: sitemap, robots, 페이지별 metadata, OG 이미지, JSON-LD(Person).
- 딥다이브 노트를 날짜 피드가 아닌 프로젝트별 그룹으로 묶는 이유: 비정기 작성(프로젝트 수행 시에만 집중 작성)이 구조상 공백으로 보이지 않게 하기 위함. 밀도로 승부하는 형식.

## 4. 케이스 스터디 템플릿

각 프로젝트 MDX는 동일한 골격을 따른다.

1. **한 줄 요약 + 메타** — 기간(git 이력 기준 시작~현재, 진행 중이면 명시), 역할(1인 전과정, 팀이면 본인 담당 명시), 스택, **라이브/GitHub 링크 버튼**(목록 카드와 상세 상단 양쪽 고정)
2. **배경** — 누가, 왜 의뢰했는가 (실제 고객 서사)
3. **문제** — 기술 문제가 아니라 사용자·운영자의 문제로 서술
4. **아키텍처** — 시스템 다이어그램 1장 (Mermaid 또는 SVG)
5. **API/파이프라인 설계 구조** — 주요 엔드포인트·잡 체인·데이터 흐름을 시각화하고, 왜 그렇게 설계했는지 서술
6. **설계 결정 3~5개** — 각각 "선택지 → 선택 → 트레이드오프" 형식
7. **실전 제약과 대응 1~3개** — 이상적 시나리오가 아니라 실제 고객·현장에서만 생기는 제약과 그 대처. 기술 선택이 "최선의 설계"가 아니라 "주어진 제약 안의 최선"이었음을 보여준다.
   - 예: 교회 유튜브 채널이 운영진 개인 Google 계정이라 공유를 받을 수 없음 → 공식 YouTube Data API(OAuth) 대신 크롤링 기반 RapidAPI yt-api로 전환
   - 예: Vercel 요청 본문 4.5MB 한도 → 브라우저 선압축·presigned URL 직접 업로드로 우회
8. **트러블슈팅 기록 발췌** — `fix:` 커밋 이력에서 대표 사례 2~4건을 "증상 → 원인 → 수정" 형식으로 재구성. 커밋 해시를 증거로 첨부한다.
9. **프론트 구현 하이라이트 1~2개** — 직접 구현한 UI/UX 디테일 (예: SSE 진행 스트림 UI, 라이트박스, 지도 인터랙션)
10. **실제 서비스 스크린샷** — 핵심 화면 2~3장
11. **운영에서 배운 것** — 장애·개선·수치 (회고)
12. **딥다이브 노트 링크**

### 콘텐츠 소재: fix: 커밋 발굴

각 저장소의 `git log --grep="^fix"`가 트러블슈팅 소재의 1차 출처다 (2026-07 기준 총 110건: ycc-website 52, korea-univ-project 24, ankang-sumgim 23, worldengco-website 11). 구현 단계에서 저장소별로 커밋을 훑어 "실전 제약" 또는 "트러블슈팅 기록" 후보 목록을 만든 뒤 케이스 스터디별로 배정한다. 대표 후보 예시:

- ycc: HWP 인라인 컨트롤 ID 본문 혼입(`d8b4625`), 설교 ingest를 채널 목록 → 단건 조회 전환(`d7588c4`), HEAD 검증의 일시 장애·404 구분(`88f81b4`)
- ankang: HEIC 거절 처리 — sharp 프리빌드에 HEVC 디코더 부재(`d03cba3`), 블러 좌표 가장자리 클램프·다중 얼굴 버그(`0b41430`), Vercel 4.5MB 한도 대응(`80f17f7`)

### 4번 프로젝트 익명화 방침

회사 홈페이지이므로 포트폴리오에는 회사명 없이 **"특장차(목욕차) 제작업체 홈페이지"** 로 게재한다.

- 회사명·대표자명·사업자번호·전화번호·주소·이메일 미표기
- 라이브 링크는 게재 (접속하면 드러나지만, 포트폴리오 문서에 검색 가능한 형태로 회사명을 남기지 않는다)
- 스크린샷에 로고·연락처가 크게 노출되면 크롭 또는 블러
- 상태는 **"v1 오픈 준비 완료 · 부품관리 확장은 고객 자료 대기"** 로 솔직히 표기. 미착수 사유(자료 없이 데이터 구조를 추측하면 재작업 확정)를 함께 적어 판단이었음을 보인다

### 성장 서사 — "진행하면서 깨달았다"

4개 프로젝트를 독립된 자랑거리로 나열하지 않고, **앞 프로젝트의 한계를 다음 프로젝트에서 해결한 연속선**으로 배치한다. 완성형 개발자를 연기하는 대신 실제로 성장한 궤적을 보여주는 것이 이 포트폴리오의 차별점이다.

근거는 git 이력에서 나온 **검증 체계 도입 시점의 단조 감소**다. 프로젝트 시작일로부터 첫 테스트·첫 CI 커밋까지 걸린 일수:

| 프로젝트      | 시작       | 첫 테스트           | 첫 CI      | 테스트까지 | CI까지         |
| ------------- | ---------- | ------------------- | ---------- | ---------- | -------------- |
| 모두의 캠퍼스 | 2026-04-27 | 2026-07-21 (E2E)    | 2026-07-23 | 85일       | 87일           |
| 안강 섬김     | 2026-05-04 | 2026-06-12 (단위)   | 2026-07-16 | 39일       | 73일           |
| 영천중앙교회  | 2026-06-06 | 2026-06-20 (Vitest) | 2026-06-22 | 14일       | 16일           |
| worldengco    | 2026-07-04 | 2026-07-11 (E2E)    | 2026-07-04 | 7일        | **0일 (당일)** |

즉 "테스트를 나중에 붙이는" 방식에서 "시작하는 날 CI부터 세우는" 방식으로 바뀌었고, 이는 AI로 빠르게 코드를 생성할수록 **동작을 고정하는 장치가 먼저 필요하다**는 깨달음의 결과다. §1의 AI 개발 방식 메시지와 이 표가 서로를 뒷받침한다.

함께 서술할 스택 진화 축:

- **언어·스타일**: JavaScript + 인라인 style(모두의 캠퍼스) → TypeScript + Tailwind(안강 이후 전부)
- **데이터 계층**: Supabase BaaS 의존 → Neon + Drizzle로 스키마·마이그레이션 직접 관리(영천) → Cloudflare D1 + Drizzle 엣지 환경(worldengco)
- **인프라**: Vercel → Cloudflare Workers(OpenNext), 배포 파이프라인을 GitHub Actions로 이관

이 서사는 홈에 3~4줄 요약으로 노출하고, About 타임라인에서 프로젝트별로 "이때 무엇이 부족해서 다음에 무엇을 바꿨는가"를 서술한다. 각 케이스 스터디 §11(운영에서 배운 것)에도 다음 프로젝트로 이어진 개선점을 한 문단씩 남긴다.

## 5. 단계별 릴리스

- **1차 (공개 가능 최소선)**: 홈 + 케이스 스터디 2개(교회·복지센터 — 운영 중인 2건) + About + CI/CD 배포 + SEO
- **2차**: 케이스 스터디 3개 추가 — 모두의 캠퍼스, 한약안전사용 플랫폼, **특장차 제작업체(실도메인 오픈 이후)** + 딥다이브 노트 3편(WebSub 파이프라인, HWP 바이너리 파싱, 얼굴 블러)
- **3차**: Workers Cron 헬스체크 → D1 적재 → 홈 상태 뱃지·응답시간 표시

4번 프로젝트를 2차로 미루는 이유: 현재 라이브가 개발용 `workers.dev` 주소이고 실도메인 연결 전이다. 저장소가 비공개라 코드 검증이 불가능하므로 **라이브 링크가 유일한 증거**이며, 실도메인 오픈 후에 작성해야 성립한다.

각 단계는 독립적으로 배포 가능해야 하며, 1차 완료 시점부터 사이트를 공개한다.

## 6. 에러 처리

- 존재하지 않는 slug: `notFound()` → 커스텀 404.
- MDX frontmatter 오류: 빌드 실패로 조기 검출 (zod 검증을 콘텐츠 로더에 내장).
- 3차 라이브 지표: 헬스체크 실패·D1 조회 실패 시 지표 영역만 숨기고 페이지는 정상 렌더 (graceful degradation).

## 7. 디자인 원칙

백엔드 포트폴리오 관례(깔끔·심플)를 따르되, 사이트 자체가 프론트 역량의 증거가 되도록 한다.

- 깔끔하고 직관적인 레이아웃. 장식성 애니메이션은 자제하고 핵심 정보(운영 중 서비스, 라이브 링크) 전달을 우선한다.
- 사이트 제목·브랜딩은 본인 이름(dongwoobae) 기반. URL 자체가 개인 브랜드다.
- 반응형, 접근성(키보드 내비게이션, 시맨틱 마크업), 로딩·전환 디테일 같은 기본기의 완성도로 FE 역량을 은근히 증명한다.
- 다이어그램·코드 블록 등 와이드 콘텐츠는 자체 스크롤 컨테이너로 처리한다.
